======================================================================
app_state - See what the GenMSI desktop app is showing right now: the model it has open (`path`), whether the reader has changes that are not saved on it (`dirty`), what the app found in that model (`diagnostics`) and the last run the app made (`run`). It returns the genmsi.live/1 document, the one the app publishes; when the app is not running the document has `path: null` —that is an answer, not a failure. Ask it BEFORE you write on the model the app has open: `apply_edit` and `save_model` refuse with `model_locked` while the app has unsaved changes on that model, so tell the reader to save it and send the same edit again.

  "properties": {},
  "type": "object"
}

apply_edit - Add, edit and connect the blocks of a GenMSI model. The commands are the engine's own editing commands, the same ones the desktop application speaks: `addBlock` {class, container, x, y} creates a block of a catalogue class (call `catalogue` first: it gives the class names, their ports (ioid) and their properties), `connect` {from, fromIoid, to, toIoid} wires an output port to an input port, `setProperty` {id, property, value} sets a declared property, `setCaption` {id, caption} names a block, `moveBlock` {id, x, y} moves one, `removeBlock` {id} takes one away and `removeBlocks` {ids} takes several away as ONE operation; the schema of the tool carries the whole vocabulary. The commands are applied in order and the batch is ATOMIC: if one fails, none is applied and the failure names the command that failed —its index, its `op`, the block it was about with the class and the name the agent gave it, and the property it was setting. `layout` says where the blocks the batch adds go: `auto` (the default) puts every block an `addBlock` adds where there is room in its container, like a drop in the application; `explicit` uses the `x` and the `y` of the command. `dry_run` tries the batch WITHOUT writing it: the commands are applied and the model is compiled, nothing is written, and the answer carries the model it would have written. The model is checked before it is written: one that does not compile is NOT written, and the error names the block that caused it. The blocks the batch creates take the next free ids, in the order of the commands. Takes `path` (a .gmdl file) or `model` (the .gmdl document as text): `path` may be left out, and then the model the app has open is the one the batch edits; a `path` that is not on the disk yet is a model the batch CREATES, and the file is written when the model compiles. `target` says where the result goes: `file` (the default) writes it to the file the batch edited, and `proposal` leaves the model in the staging area of the app, without touching the disk, where the person sees it and decides to accept it or to discard it — the verdict comes back in `app_state`. `summary` is one line about what the batch did; it travels with the proposal. Returns the genmsi.edit/1 document.

catalogue - Describe the block classes a GenMSI model is built from. Call it BEFORE writing a model: it tells you which classes exist, what each one does (its description), which ports (ioid) and properties (name, hint, ty, subtype) each class declares, which entities the class declares and which it uses, and the exact XML of a block of that class —with the default value of each property— so you never have to guess an element name. Without arguments it returns the genmsi.classlist/1 document (every class plus the skeleton of a model). With `class` (for example "Generate") it returns the genmsi.class/1 document of that class; with `classes` (a list of names) it returns the genmsi.classes/1 document with every class asked for, so an agent that needs several classes asks for them all in ONE call.

explain_model - Describe a GenMSI model: its blocks, operands and ports, plus what each GPSS statement of the model does. Takes `path` (a .gmdl file) or `model` (the .gmdl document as text) and returns the genmsi.explain/1 document. The document has three parts: `program` is the compiled GPSS (one entry per statement, with the block of the document it came from and the line and column of that block in the .gmdl), `model` is the document itself, with every block, its properties by name and the links that wire the blocks, and `map` joins the two: one row per compiled statement, with the `node` of the block of the document it came from, the class of that statement, the name the agent gave the block (its `caption`) and the line and column of the block in the .gmdl. With the `node` that every event of the trace carries, the map answers "what block is the statement 218?" in one line.

get_trace - Simulate a GenMSI model and return its event trace, or —with `summary`— the summary of the run. Takes `path` or `model`, plus the optional `seed`, `until`, `start` and `limit`, and returns the genmsi.trace/1 document. The trace can be FILTERED: `classes` keeps only the events of those block classes ("Queue", "Terminate", ...), `nodes` keeps only the events of those blocks of the document (their `moduleid`, the `node` every event carries), `xact` keeps only the events of that transaction, and `from` and `to` keep only the events of that window of simulated time (the window is closed at both ends; `until` is something else: it is the horizon of the run). The filter is applied in the engine WHEN THE EVENT IS RECORDED, so `limit` counts the events that pass the filter and not the events of the run: asking for the events of one class gives those events, not the first ones of the run. Without a filter the answer is the whole trace, exactly as before. With `summary: true` the tool answers the genmsi.trace_summary/1 document instead: for every block, how many times the flow went through it and the first and the last time it went through it — the question the agent asks the ninety percent of the time ("how many times did the flow go through here?") — and not the events. The summary is the summary of the WHOLE run, and the filters do not cut it.

save_model - Write a GPSS model to a .gmdl file. The model is checked before it is written: one that does not load, does not validate or does not compile is NOT written, and the error names the block that caused it. A model that carries no canvas geometry is composed before it is written, so the editor can draw it; a model that already carries its geometry keeps the disposition its author left. Takes `model` (the whole .gmdl document as text, not a patch) and `path` (the file to write): `path` may be left out, and then the model the app has open is the one that is written. `target` says where the model goes: `file` (the default) writes it to that file, and `proposal` leaves the model in the staging area of the app, without touching the disk (the `path` is not written to), where the person sees it and decides to accept it or to discard it — the verdict comes back in `app_state`. `summary` is one line about what the agent did; it travels with the proposal. Returns the genmsi.lint/1 document of what was written. Use it to create or to change a model: read it first with explain_model, change the text and hand the complete document back.
